# Preprocessor Review Against Coral 66 Specification

This document presents a review of the preprocessor code (`lib/frontend/preprocessor`) against the provided Coral 66 language specification documents (`Official Definition of Coral 66.txt/pdf` and `coral66-grammar.txt`). The review identifies areas mandated by the specifications that are not supported by the current codebase, as well as areas supported by the codebase that are not mandated by the specifications.

## 1. Mandated by Specification, NOT Supported by Code

### 1.1 Formal and Actual Parameter Naming Restrictions
**Specification Constraint**: The Official Definition explicitly states:
> *"no identifier in an actual parameter string, or its subsequent expansions, may be the same as any formal parameter of the calling macro."*

**Implementation Status**: The preprocessor logic in `macroSubstitute` does not cross-check the identifiers present in `actual_args` against the formal parameter names (`params`). It accepts matching identifiers without logging any diagnostic errors or terminating substitution, which violates the strict naming rules intended to prevent expansion ambiguity and infinite recursion in Coral 66.

### 1.2 Nested Macro Definition Constraints
**Specification Constraint**: The Official Definition states:
> *"A formal parameter may not be used in any inner nested macro definition, neither in its body nor as a macro name nor as a formal parameter."*

**Implementation Status**: There is no semantic validation within `Preprocessor::parseDefineDirective` (nor during macro substitution) to verify if an inner `DEFINE` directive illegally leverages formal parameters from the outer macro scope.

### 1.3 Execution of Directives Generated by Macro Expansions
**Specification Constraint**: The Official Definition implies that macro expansions can produce other macros dynamically:
> *"A macro definition may embody definitions or uses of other macros to any depth..."* 

**Implementation Status**: The preprocessor is designed such that `preprocessor_parser.cpp` runs first over the token stream, extracting `DefineDirective` and `DeleteDirective` elements *before* any macro expansion occurs. When `Preprocessor::visit(const TextBlock&)` invokes `macroSubstitute`, any occurrences of `DEFINE` or `DELETE` that result from evaluating a macro body are blindly pushed to the output token stream as raw `DefineKeyword` and `DeleteKeyword` tokens. They are never rescanned or executed as preprocessor control directives, effectively disabling dynamically generated macro definitions from being processed.

### 1.4 Protection Against Infinite Recursion
**Specification Constraint**: By forbidding parameters that evaluate to formal parameters, the specification logically guards against recursive evaluation problems.

**Implementation Status**: While the header `preprocessor.hpp` declares an `m_disabledMacros` container intended for cycle detection (similar to C-style blue-painting), the variable is unused in `preprocessor.cpp`. The preprocessor will loop infinitely (or cause a stack overflow) if a user defines and invokes a self-referencing macro.

## 2. Supported by Code, NOT Mandated by Specification

### 2.1 C-Style Expression Evaluation (`evaluateExpression`)
**Code Implementation**: Both `preprocessor.hpp` and `preprocessor.cpp` declare and define an `evaluateExpression` method. This method iterates over tokens, parsing them into `llvm::APSInt` literals and attempting to evaluate logical/arithmetic components. It resembles the evaluation of C-style conditional preprocessor directives (e.g., `#if`, `#elif`).

**Specification Conflict**: The Coral 66 specification defines no such conditional preprocessor facility. The macro facility consists solely of `DEFINE` and `DELETE` string/token replacement commands, along with standard `COMMENT` sequences. There are no `#if` or `#endif` directives in Coral 66. As a result, `evaluateExpression` is unmandated, orphaned dead code that falls completely outside the scope of the language definition.

## Conclusion

The Coral 66 preprocessor implementation successfully implements the foundational `DEFINE` and `DELETE` keywords, argument comma-protection parsing (nested parenthesis and square bracket tracking), and macro definition stacking/popping. However, to achieve full compliance with the strict constraints of the Official Coral 66 Definition, the codebase needs additional validation sweeps for actual vs. formal parameter identifier conflicts, and an architectural adjustment to process control directives injected during macro expansion. The unmandated `evaluateExpression` method should be removed to eliminate dead-code overhead.
